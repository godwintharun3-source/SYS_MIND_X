# Architecture Decision Log

## ADR-001: AI is the high-level control plane; native kernels remain the execution foundation
Status: proposed baseline. The model plans and explains. Trusted brokers and native OS APIs execute bounded operations.

## ADR-002: Cross-platform adapters
Status: proposed baseline. Use one capability contract and separate macOS, Windows and Linux adapters.

## ADR-003: Start with macOS companion agent, then NixOS VM, then Windows
Status: proposed baseline. Keep the developer's host safe; validate OS changes in disposable VMs.

## ADR-004: SQLite first
Status: proposed baseline. Start with SQLite and event tables; introduce PostgreSQL/graph storage only when measured needs justify it.

## ADR-005: No unrestricted file execution
Status: non-negotiable. Trust is evidence-based and time-sensitive. Unknown files are isolated or handled by a restricted viewer.

## ADR-006: System updates exclude user applications
Status: non-negotiable. Maintain component ownership and never silently update user-installed apps or project dependencies.

## ADR-007: Persistent files, not chat history, are project memory
Status: non-negotiable. Every daily agent session reloads project state from repository files.

## ADR-008: Machine-Enforceable Charter Contracts and Read-Only Host Telemetry
Status: accepted. Charter boundaries (rejection of raw root/shell, strict exclusion of user applications from autonomous updates, zero-trust execution confinement, explicit approvals for critical operations) are implemented as typed contracts and deterministic validators rather than natural-language instructions alone. Non-destructive host inspection verifies environment facts (Apple Silicon M1, SIP, Gatekeeper) without mutating host system configuration.

## ADR-009: Persona-Driven Contextual Governance Envelopes
Status: accepted. SYSTEM MIND X enforces distinct contextual governance envelopes for Personal, Developer, and Enterprise Admin personas. Personal users are bounded to Low/Medium impact with strict privacy perimeter protection; Developers have scoped high-impact workspace capabilities with absolute protection against autonomous dependency updates; Enterprise Admins have full audit visibility and require dual-person or break-glass approval for critical privileged actions.

## ADR-010: State-Machine User Journey Execution, Compensation Rollback, and Quantitative Outcomes
Status: accepted. User journeys are structured as formal state-machine step sequences. Every step enforces independent policy checks, preconditions, broker execution, postconditions, and audit records. Any mid-sequence failure triggers automatic reverse-chronological compensation rollbacks. Journey success is evaluated against strict quantitative metrics (latency, non-interference invariants, containment isolation, audit completeness).

## ADR-011: Granular Capability-Level Platform & Hardware Support Matrix
Status: accepted. The first-release support matrix is strictly bounded to four verified platform profiles: macOS on Apple Silicon M1 (Tier 1 Development Host & Companion), Windows 11 x64 (Tier 2 Companion), Ubuntu LTS x86_64 (Tier 2 Companion), and NixOS VM (Tier 3 Prototype OS). Operating system APIs are not treated as fungible; every engine capability must be explicitly tagged as SUPPORTED, PARTIAL (with documented limitations), or MOCK_ONLY. Uncertified platforms (Intel macOS, Windows 10/32-bit, non-systemd Linux) are rejected by policy.

## ADR-012: Countermeasure Architecture Derived from Prior Art Failure Modes
Status: accepted. Systematic analysis of current AI-native OS and computer-use agent prior art identifies six core failure modes: Ambient Authority Abuse (F1), Prompt Injection via Uncontained Inputs (F2), Hallucinated Destructive Execution (F3), Irreversible State Drift (F4), Ambient Screen Scraping Privacy Leaks (F5), and Component Ownership Contamination (F6). SYSTEM MIND X incorporates explicit architectural countermeasures rejecting all six patterns through typed broker mediation, deterministic policy verification, zero ambient screen recording, and strict component ownership protection.

## ADR-013: Research-Gap Closure via Independent Policy Broker and Component Segregation
Status: accepted. Benchmarking against seven competitive and prior art systems across eight core dimensions establishes that SYSTEM MIND X addresses five critical industry research gaps: Gap 1 (AI-Native Policy-Broker Disconnect), Gap 2 (Component Ownership Vacuum & Dependency Clobbering), Gap 3 (The 'Scan is Safe' Fallacy & Ambient Host Execution), Gap 4 (Screen Ephemerality vs Persistent Temporal Digital Twin), and Gap 5 (The All-or-Nothing Privilege Trap). Full native compliance across all dimensions is enforced as an architectural invariant.

## ADR-014: Six-Zone Trust Boundary Architecture and STRIDE Threat Model
Status: accepted. SYSTEM MIND X formally stratifies system operations across six hierarchical Trust Zones (Zone 0: Untrusted External, Zone 1: User Space, Zone 2: AI Control Plane, Zone 3: Deterministic Policy Engine, Zone 4: Privileged Broker, Zone 5: Kernel & Hardware). Transitions must strictly obey the Rule of Strict Adjacency (AI Control Plane Zone 2 cannot bypass Policy Engine Zone 3 to reach Broker Zone 4 or Kernel Zone 5) and the Rule of Untrusted External Non-Execution (Zone 0 binaries can never execute in Zone 1/5 without verified containment). All six STRIDE threat categories (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) are cataloged into typed threat vectors with verified architectural mitigations.

## ADR-015: Operation Classification Taxonomy, Privilege Levels, and Reversibility
Status: accepted. All SYSTEM MIND X system operations are categorized across three orthogonal dimensions: Impact (OperationRiskTier: READ_ONLY to CRITICAL_PRIVILEGED), Privilege Level (PrivilegeLevel: UNPRIVILEGED_USER, USER_CONSENT_GRANTED, ELEVATED_BROKER_REQUIRED, HARDWARE_FIRMWARE_ENTITLED), and Reversibility (Reversibility: REVERSIBLE, PARTIALLY_REVERSIBLE, IRREVERSIBLE) paired with concrete rollback strategies (RollbackStrategy: ATOMIC_FILE_RESTORE, STATE_INVERSE_ACTION, TRANSACTIONAL_SNAPSHOT, NOT_REVERSIBLE_COMPENSATION_ONLY). Autonomous unattended maintenance is strictly limited to SYSTEM_MANAGED components with risk not exceeding MEDIUM_IMPACT; USER_MANAGED components and HIGH_IMPACT / CRITICAL_PRIVILEGED operations are strictly excluded.

## ADR-016: Formal Product Non-Goals and Explicit Safety Constraints
Status: accepted. SYSTEM MIND X formalizes ten explicit Product Non-Goals (NG-01 to NG-10: no unrestricted shell, no ambient screen OCR, no autonomous user-app mutation, no scan-means-safe native execution, no security control bypass, no mandatory cloud exfiltration, no unbounded fleet mutation, no monolithic kernel from scratch, no unattended firmware flashing, no speculative capability fabrication). These negative requirements are enforced at runtime through eight machine-enforceable safety constraints (SC-01 to SC-08) by the SafetyConstraintValidator, providing hard non-bypassable architectural gates before broker execution.

## ADR-017: Core Research Questions and First-Release Acceptance Gates
Status: accepted. SYSTEM MIND X formalizes eight foundational research questions (RQ-01 to RQ-08) covering policy-broker decoupling, component ownership segregation, zero-trust file containment, temporal digital twin fidelity, contextual persona governance, automated compensation rollback, cross-platform capability parity, and zero ambient authority. All software increments and releases must programmatically satisfy eight First-Release Acceptance Gates (AG-01: Functional Completeness, AG-02: Tests & Regression Pass, AG-03: Security & Trust Boundaries, AG-04: Reliability & Rollback, AG-05: Platform Matrix Verification, AG-06: Documentation & Architecture, AG-07: Evidence & Secret Redaction, AG-08: Human Review & Day Gate) evaluated by ReleaseGateVerifier.

## ADR-018: Functional Requirements and Pipeline Topology for the Fourteen Intelligence Engines
Status: accepted. SYSTEM MIND X formalizes the functional requirements, input/output schemas, error states, and safety boundaries for all fourteen specialized intelligence engines (ENG-01 to ENG-14). Rather than routing OS execution through an undifferentiated monolithic LLM, system operations must traverse a verified pipeline topology: observation engines (Sensors, App Context, Companions) feed the Temporal Digital Twin; synthesis engines (Knowledge Retrieval, Caretaker, Developer Intelligence, Autonomous Maintenance) feed the Adaptive Governance & Policy Engine; and the Policy Engine verifies typed contracts before passing them to the Risk-Adaptive Verified Execution Broker and sandboxing adapters. Direct bypass of governance or execution boundaries is strictly prohibited.

## ADR-019: Non-Functional Requirements Framework for Reliability, Privacy, and Performance
Status: accepted. SYSTEM MIND X formalizes fifteen measurable Non-Functional Requirements across four categories: Reliability (NFR-REL-01: rollback convergence <= 5000ms, NFR-REL-02: crash recovery <= 500ms, NFR-REL-03: 99.99% uptime, NFR-REL-04: 100% pre/post assertion), Privacy (NFR-PRIV-01: 0 cleartext secrets, NFR-PRIV-02: 0 ambient screen OCR frames, NFR-PRIV-03: 100% offline local autonomy, NFR-PRIV-04: 100% cryptographic audit chains), Performance (NFR-PERF-01: policy evaluation P95 <= 5.0ms, NFR-PERF-02: twin convergence <= 50.0ms, NFR-PERF-03: companion memory <= 50 MB RSS, NFR-PERF-04: idle CPU <= 0.5%, NFR-PERF-05: broker IPC overhead <= 25.0ms), and Safety (NFR-SAFE-01: 0 user-managed app modifications, NFR-SAFE-02: 100% zero-trust binary containment). All requirements are enforced programmatically by NfrComplianceEvaluator.

## ADR-020: Seven-Layer System Architecture and Inter-Layer Component Boundaries
Status: accepted. SYSTEM MIND X establishes a strict Seven-Layer System Architecture: Layer 1 (Presentation & Interface), Layer 2 (Cognitive Planning & Context Plane), Layer 3 (Deterministic Policy & Governance Engine), Layer 4 (Temporal Digital Twin & Provenance Store), Layer 5 (Narrow Privileged Execution Broker), Layer 6 (Platform Capability Adapters & Sandboxing), and Layer 7 (Native OS Kernel & Physical Hardware). Inter-layer communication is enforced programmatically by ArchitectureBoundaryEnforcer according to three cardinal invariants: the Rule of Strict Adjacency (Layer 2 cannot bypass Layer 3 to directly invoke Layer 5, 6, or 7), Directional Separation (downward execution requests vs upward telemetry/event observations), and Autonomous Non-Interference with user-managed components.

## ADR-021: AI Cognitive Plane as an Untrusted Planner Isolated in User Space
Status: accepted. The AI cognitive plane runs in unprivileged user space with zero OS mutation rights and communicates outward solely via typed declarative ActionContracts. All consequential actions require downstream deterministic policy approval, ensuring prompt injections cannot trigger native system calls.

## ADR-022: Narrow Privileged Execution Broker with Cryptographic Provenance and Atomic Rollback
Status: accepted. Consequential state modifications are dispatched exclusively through a narrow broker daemon that validates preconditions, enforces atomic rollbacks upon postcondition failure, and logs immutable SHA-256 audit receipts. Ambient shell execution is eliminated.

## ADR-023: Deterministic Non-LLM Invariant Firewall as Authority Gate
Status: accepted. An independent deterministic rules engine operating strictly outside LLM weights evaluates all proposed contracts against charter invariants and component ownership boundaries. The AI model cannot convince or bypass the policy engine, and policy evaluation is mathematically guaranteed.

## ADR-024: Native OS Kernel and Security Controls as Authoritative Enforcers
Status: accepted. Native OS kernels remain the authoritative lower-level security enforcement boundary. SYSTEM MIND X works strictly within native OS entitlements and never disables or weakens native security controls (SIP, Gatekeeper, WDAC, AppArmor).

## ADR-025: Cross-Platform Capability Parity Levels and Adapter Contracts
Status: accepted. Operating systems are fundamentally non-fungible and cannot be flattened into a lowest-common-denominator abstraction. SYSTEM MIND X formalizes a five-tier capability parity hierarchy (LEVEL_1_FULL_PARITY, LEVEL_2_EQUIVALENT_PARITY, LEVEL_3_DEGRADED_PARITY, LEVEL_4_EMULATED_SIMULATED, LEVEL_5_UNSUPPORTED) across eight core domains (FS_OBSERVATION, PROCESS_TELEMETRY, HARDWARE_TELEMETRY, FILE_PROVENANCE, EXECUTION_CONTAINMENT, SYSTEM_SNAPSHOT_ROLLBACK, SYSTEM_PACKAGE_MAINTENANCE, SECURITY_AUTHORITY_ENFORCEMENT). The CapabilityParityEvaluator enforces typed contracts, documented degradation warnings, and mandatory fallback strategies before broker dispatch, ensuring zero capability hallucination or security dilution.

## ADR-026: Digital-Twin Entity and Relationship Model and Graph Referential Integrity
Status: accepted. SYSTEM MIND X implements a typed, in-memory directed property graph in Layer 4 (DigitalTwinGraph) to represent observed host state across hardware, processes, files, packages, and security postures. The graph models 10 entity types and 9 relationship types with mandatory tripartite component ownership (SYSTEM_MANAGED, VENDOR_MANAGED, USER_MANAGED), provenance attribution, cascading relationship deletion upon entity removal, and strict prohibition of cleartext sensitive credentials.

## ADR-027: Temporal Observations, Cryptographic Provenance, and Bounded Freshness Enforcement
Status: accepted. SYSTEM MIND X augments the Digital Twin with an append-only TemporalTimelineStore that logs discrete observations with strictly monotonic sequence numbers, SHA-256 payload integrity hashing, and provenance verification status (VERIFIED_KERNEL, VERIFIED_BROKER, UNVERIFIED_USER_SPACE). The FreshnessEvaluator computes staleness decay scores across configurable TTL windows (FRESH, AGING, STALE, EXPIRED, TOMBSTONED), and the policy engine enforces a Staleness Guard blocking consequential mutating dispatches against stale target entities.

## ADR-028: Application Ownership Classification and User-App Exclusion Model
Status: accepted. SYSTEM MIND X implements a dedicated ApplicationOwnershipClassifier and UserAppExclusionEnforcer. All host software is categorized into the tripartite ownership model (SYSTEM_MANAGED, VENDOR_MANAGED, USER_MANAGED) with a fail-safe default of USER_MANAGED. All user-installed applications, desktop browsers, IDEs, and developer virtual environments are permanently excluded from autonomous system maintenance pipelines and require explicit human consent (user_approved=True) before any mutation can occur.

## ADR-029: System-Update Ownership Taxonomy and Safety Lifecycle
Status: accepted. SYSTEM MIND X formalizes a six-tier System-Update Ownership Taxonomy (OS_SECURITY_HOTFIX, SYSTEM_DAEMON_MAINTENANCE, OS_CUMULATIVE_UPDATE, FIRMWARE_HARDWARE_UPDATE, USER_APP_UPDATE, PROJECT_DEPENDENCY_UPDATE). Autonomous unattended execution is restricted exclusively to Tier 1 and Tier 2. Cumulative OS updates require pre-update filesystem recovery snapshots and user-scheduled reboot maintenance windows. Firmware updates require explicit human consent, recovery snapshots, and AC power verification. User applications and project dependencies remain strictly excluded from autonomous system updates.

## ADR-030: File Trust State Machine and Supported File-Handler Policy
Status: accepted. SYSTEM MIND X formalizes a discrete eight-state File Trust State Machine (UNTRUSTED_UNKNOWN, QUARANTINED, STATICALLY_INSPECTED, SANDBOX_VERIFIED, USER_ATTESTED, VENDOR_SIGNED_VERIFIED, SYSTEM_CORE_IMMUTABLE, BLOCKED_MALICIOUS) and a Supported File-Handler Policy (DENIED, STATIC_PARSER_ONLY, HARDENED_ISOLATED_VIEWER, DISPOSABLE_SANDBOX_EXECUTION, NATIVE_HOST_EXECUTION). Under the inviolable 'Scan != Safe' invariant, static inspection or antivirus clearing moves a file to STATICALLY_INSPECTED at best and strictly prohibits native host execution. Quarantined and untrusted files are restricted to unprivileged static parsers or isolated micro-VM sandboxes. Native host execution is strictly restricted to immutable OS core binaries, verified vendor-signed binaries, or user-attested files with explicit human consent.

## ADR-031: Typed Action Contracts, Precondition/Postcondition Rules, and Atomic Rollback
Status: accepted. SYSTEM MIND X replaces unstructured shell commands with strongly typed action contracts (TypedActionContract) governed by deterministic Precondition and Postcondition rules. Consequential operations (MEDIUM_IMPACT, HIGH_IMPACT, CRITICAL_PRIVILEGED) strictly mandate explicit pre-execution readiness predicates and post-execution state verification predicates. High and critical operations mandate an executable RollbackContract (snapshot revert, file restore, service restore, or package downgrade). Contract parameters are sanitized against shell metacharacters and command injection patterns. The Layer 6 Trusted Broker is mathematically prohibited from capability dispatch if any precondition fails, and automatically invokes the rollback contract if any postcondition fails.

## ADR-032: Identity, Role-Based Authority, and Deterministic 4-Tier Policy Precedence
Status: accepted. SYSTEM MIND X formalizes explicit caller identities (LOCAL_CONSOLE_USER, AI_COGNITIVE_PLANNER, AUTONOMOUS_MAINTENANCE_DAEMON, ENTERPRISE_MDM_ADMIN, SANDBOXED_PEER_AGENT) and role-based authority boundaries (SecurityRole). The PolicyPrecedenceEngine resolves authorization through a strict, deterministic four-tier hierarchy: Tier 1 (Supreme) Hard Charter Invariants (SC-01 to SC-08), Tier 2 Enterprise Organization Policies, Tier 3 User Explicit Safety Policies, and Tier 4 AI Planner Heuristic Proposals. Higher tiers strictly override lower tiers; Tier 1 hard invariants cannot be bypassed by any user, administrator, or enterprise policy. Dual authorization (TWO_PERSON_OR_BREAK_GLASS) mandates confirmed biometric authentication for critical privileged operations.

## ADR-033: Immutable Cryptographic Audit Ledger, Automated Secret Redaction, and Tiered Data Retention
Status: accepted. SYSTEM MIND X implements an append-only, tamper-evident cryptographic audit ledger (ImmutableAuditLedger) in Layer 6. Every consequential action, policy decision, approval, capability dispatch, state mutation, and rollback is recorded with strictly monotonic sequence numbers, canonical payload hashes, and SHA-256 hash-chain linkage (prev_event_hash). The SecretRedactor recursively scrubs credentials, API tokens, passwords, session tokens, and private keys before hashing or persistence. A 5-tier data retention taxonomy governs storage lifecycles (from 48-hour ephemeral traces to 365-day immutable critical security events). When expired non-critical records are pruned, a ChainCheckpointRecord anchors the hash chain, maintaining unbroken mathematical verification.

## ADR-034: Unified API Wire Envelopes, RFC 7807 Structured Error Model, and SemVer Negotiation
Status: accepted. SYSTEM MIND X standardizes IPC and service communications across all execution planes through typed Request (`ApiRequest`) and Response (`ApiResponse`) wire envelopes, an RFC 7807-inspired structured error model (`ApiErrorDetail`), and SemVer 2.0.0 client-server negotiation (`VersionNegotiator`). Wire envelopes mandate globally unique request IDs, dot-delimited method URNs, caller identity headers, and mandatory idempotency keys (`idempotency_key`) for all mutating operations to prevent duplicate execution. Machine-readable error codes (`E1000..E7999`) across seven functional domains enforce actionable remediation hints and retryability semantics, while `ApiErrorFactory` integrates with `SecretRedactor` to guarantee recursive scrubbing of API tokens, passwords, and private credentials from diagnostic error payloads. Major version changes enforce a minimum 6-month deprecation warning cycle before method retirement.

## ADR-036: Monorepo Topology, Top-Level Workspace Boundaries, and Dependency Isolation
Status: accepted. SYSTEM MIND X organizes the codebase as a strictly boundary-enforced polyglot monorepo governed by a machine-readable manifest (`monorepo.json`), boundary documentation per zone (`README.md`), and automated CI verification (`MonorepoBoundaryValidator`). Six canonical top-level zones partition the system: `apps/` (Layer 7 Desktop UI in TypeScript/React & Tauri), `crates/` (Layer 1, 2, 6 Native Daemon and OS sensors in Rust), `src/` (Layer 3, 4, 5, 6 Cognitive Planner, Digital Twin, and Policy in Python), `schemas/` (Layer 6, 7 language-neutral contracts in JSON Schema / Cap'n Proto), `tools/` (developer tooling and release verification), and `docs/` (architectural specifications). To uphold architectural security invariants, strict unidirectional dependency rules are enforced: `apps/` and `src/` cannot directly import internal `crates/` source or call native OS APIs without wire mediation; `crates/` cannot depend on Python runtimes; `schemas/` must remain completely self-contained; and `tools/` cannot be packaged into production daemon or UI artifacts.

## ADR-037: Python Backend Package Specification, Strict Dependency Pinning, and Deterministic Packaging Standards
Status: accepted. SYSTEM MIND X standardizes the Python Control Plane package (`system-mind-backend` v1.0.0) using PEP 517 / PEP 518 / PEP 621 compliant `pyproject.toml` metadata and exact dependency pinning (`requirements.txt`, `requirements-dev.txt`). To uphold safety-critical reliability and zero-ambient-execution guarantees, core domain models, state machines, and validators prioritize Python's standard library to minimize supply-chain surface area. Strict pinning (`package==X.Y.Z`) is enforced across all dependency declarations, while ambient execution wrappers (e.g. `sh`, `plumbum`, `pexpect`) are banned from production requirements. The package exposes a safe, non-privileged administrative introspection entrypoint (`system-mind`), and `PackageConfigValidator` verifies metadata, dependency locks, and entrypoints in CI pipelines.

## ADR-038: Rust System-Agent Workspace Architecture and Crate Boundary Invariants
Status: accepted. SYSTEM MIND X organizes the native system agent as a multi-crate Cargo workspace (`crates/`) partitioned into three strictly segregated, acyclic crates: `system-mind-common` (foundational domain types, capability IDs, privilege levels, error taxonomy, and payload fingerprints), `system-mind-sensors` (Layer 1/2 hardware sensor abstractions and mock/native telemetry collectors), and `system-mind-broker` (Layer 6 narrow privileged capability broker daemon). Dependency flow is strictly unidirectional (`system-mind-broker` -> `system-mind-sensors` -> `system-mind-common`). The crates compile as standalone, memory-safe native binaries with zero dependency on Python runtime environments (`libpython`) or raw shell wrappers. The broker mathematically enforces the inviolable "Scan != Safe" invariant and the tripartite application ownership guard before capability dispatch. The `RustWorkspaceValidator` programmatically enforces crate boundaries and acyclic constraints in CI.

## ADR-039: React and TypeScript Desktop Frontend Scaffold, Presentation Layer Boundaries, and Wire Client Protocol
Status: accepted. SYSTEM MIND X establishes the desktop frontend presentation workspace (`apps/desktop/`, package `@system-mind/desktop` v1.0.0) built on TypeScript, React 18, and Vite. In accordance with ADR-013, ADR-021..024, and ADR-036, the presentation layer operates in a sandboxed execution context: ambient OS shell invocation packages (`child_process`, `execa`, `shelljs`, `sudo-prompt`) are strictly prohibited from frontend dependencies. All communication with the Python Control Plane and Rust Broker routes exclusively through typed `ApiRequest` and `ApiResponse` wire envelopes with client-generated UUIDv4 `idempotency_key` tokens on mutating operations. The operator interface exposes high-contrast, accessible visualizers for live sensor telemetry, tripartite component boundaries (SYSTEM_MANAGED, VENDOR_MANAGED, USER_MANAGED), the 8-state file trust lifecycle with prominent 'Scan != Safe' guardrails, and the tamper-evident cryptographic audit ledger. The `FrontendScaffoldValidator` programmatically audits directory completeness, package dependencies, compiler strictness, and wire contract fidelity in CI.

## ADR-040: Tauri Desktop Presentation Shell, Minimal Safe Window Invariants, and Airtight Content Security Policy
Status: accepted. SYSTEM MIND X encapsulates the operator console within a native desktop presentation shell using Tauri v2 (`apps/desktop/src-tauri/`, package `system-mind-desktop` v1.0.0). In accordance with SC-01 (Zero Ambient Shell Authority) and ADR-039, the Tauri shell enforces four strict presentation security invariants: (1) Ambient child process execution permissions (`shell:allow-execute`, `shell:allow-spawn`) are permanently excluded from capability declarations (`capabilities/default.json`); (2) The main window configuration (`tauri.conf.json`) enforces `fullscreen: false` by default with centered, decorated boundaries (1280x860 default, 960x640 minimum) to ensure continuous operator awareness of native OS alerts and desktop context; (3) The webview operates under an airtight Content Security Policy (`default-src 'self'`) blocking untrusted external script loading or unmediated remote exfiltration; and (4) The native crate compiles as an independent workspace with standalone unit tests. The `TauriShellValidator` enforces window geometry, CSP rules, capability exclusions, and manifest validity in CI pipelines.

## ADR-041: Language-Neutral Canonical JSON Schemas, Polyglot Type Generation Strategy, and Cross-Language Parity Enforcement
Status: accepted. SYSTEM MIND X establishes `schemas/` as the single canonical, language-neutral source of truth across Python, TypeScript, and Rust execution domains using JSON Schema (Draft 2020-12). Five canonical domain schemas govern system boundaries: (1) `api_envelope.schema.json` (ApiRequest, ApiResponse, RFC 7807 problem details, error codes E1000..E7999, mutating idempotency keys); (2) `file_trust.schema.json` (discrete 8-state trust progression, handler execution modes, SC-03 'Scan != Safe' invariant); (3) `component_ownership.schema.json` (tripartite SYSTEM_MANAGED, VENDOR_MANAGED, USER_MANAGED ownership and update exclusion rules); (4) `action_contract.schema.json` (typed capability contracts, 5 risk tiers, pre/postconditions, rollback contracts); and (5) `audit_event.schema.json` (cryptographic SHA-256 hash chains, actor URNs, tiered data retention). The `TypeGenerator` tool (`tools/generate_types.py`) provides deterministic type generation and dry-run synchronization, while `SchemaStrategyValidator` verifies JSON Schema draft compliance and mathematically audits cross-language enum parity across all target files in CI.

## ADR-042: Multi-Language Code Quality, Formatting, Linting, and Static AST Analysis Framework
Status: accepted. SYSTEM MIND X standardizes multi-language formatting, linting, and static analysis configurations across all monorepo tiers: Python (`pyproject.toml` [tool.black], [tool.mypy], [tool.ruff], and `.flake8`), Rust (`rustfmt.toml` and `clippy.toml`), and TypeScript (`apps/desktop/.eslintrc.json` and `.prettierrc.json`). To safeguard charter invariants, static analysis configurations enforce: (1) Zero ambient shell executions: Python AST checker and Flake8/Ruff forbid `os.system` and `subprocess(..., shell=True)`, and ESLint forbids `child_process`, `execa`, and `eval`; (2) Bounded cognitive complexity and strict typing; and (3) Automated pre-commit checks (`.pre-commit-config.yaml`). The unified developer CLI tool (`tools/lint.py`) orchestrates multi-language verification locally in unprivileged user space, and `CodeQualityValidator` verifies configuration integrity and absence of security waivers in CI.
