# Architecture Decision Log

## ADR-001: AI is the high-level control plane; native kernels remain the execution foundation
Status: proposed baseline. The model plans and explains. Trusted brokers and native OS APIs execute bounded operations.

## ADR-002: Cross-platform adapters
Status: proposed baseline. Use one capability contract and separate macOS, Windows and Linux adapters.

## ADR-003: Start with macOS companion agent, then NixOS VM, then Windows
Status: proposed baseline. Keep the developer's host safe; validate OS changes in disposable VMs.

## ADR-004: SQLite first
Status: proposed baseline. Start with SQLite and event tables; introduce PostgreSQL/graph storage only when measured needs justify it.

## ADR-005: No unrestricted file execution
Status: non-negotiable. Trust is evidence-based and time-sensitive. Unknown files are isolated or handled by a restricted viewer.

## ADR-006: System updates exclude user applications
Status: non-negotiable. Maintain component ownership and never silently update user-installed apps or project dependencies.

## ADR-007: Persistent files, not chat history, are project memory
Status: non-negotiable. Every daily agent session reloads project state from repository files.

## ADR-008: Machine-Enforceable Charter Contracts and Read-Only Host Telemetry
Status: accepted. Charter boundaries (rejection of raw root/shell, strict exclusion of user applications from autonomous updates, zero-trust execution confinement, explicit approvals for critical operations) are implemented as typed contracts and deterministic validators rather than natural-language instructions alone. Non-destructive host inspection verifies environment facts (Apple Silicon M1, SIP, Gatekeeper) without mutating host system configuration.

## ADR-009: Persona-Driven Contextual Governance Envelopes
Status: accepted. SYSTEM MIND X enforces distinct contextual governance envelopes for Personal, Developer, and Enterprise Admin personas. Personal users are bounded to Low/Medium impact with strict privacy perimeter protection; Developers have scoped high-impact workspace capabilities with absolute protection against autonomous dependency updates; Enterprise Admins have full audit visibility and require dual-person or break-glass approval for critical privileged actions.

## ADR-010: State-Machine User Journey Execution, Compensation Rollback, and Quantitative Outcomes
Status: accepted. User journeys are structured as formal state-machine step sequences. Every step enforces independent policy checks, preconditions, broker execution, postconditions, and audit records. Any mid-sequence failure triggers automatic reverse-chronological compensation rollbacks. Journey success is evaluated against strict quantitative metrics (latency, non-interference invariants, containment isolation, audit completeness).

## ADR-011: Granular Capability-Level Platform & Hardware Support Matrix
Status: accepted. The first-release support matrix is strictly bounded to four verified platform profiles: macOS on Apple Silicon M1 (Tier 1 Development Host & Companion), Windows 11 x64 (Tier 2 Companion), Ubuntu LTS x86_64 (Tier 2 Companion), and NixOS VM (Tier 3 Prototype OS). Operating system APIs are not treated as fungible; every engine capability must be explicitly tagged as SUPPORTED, PARTIAL (with documented limitations), or MOCK_ONLY. Uncertified platforms (Intel macOS, Windows 10/32-bit, non-systemd Linux) are rejected by policy.

## ADR-012: Countermeasure Architecture Derived from Prior Art Failure Modes
Status: accepted. Systematic analysis of current AI-native OS and computer-use agent prior art identifies six core failure modes: Ambient Authority Abuse (F1), Prompt Injection via Uncontained Inputs (F2), Hallucinated Destructive Execution (F3), Irreversible State Drift (F4), Ambient Screen Scraping Privacy Leaks (F5), and Component Ownership Contamination (F6). SYSTEM MIND X incorporates explicit architectural countermeasures rejecting all six patterns through typed broker mediation, deterministic policy verification, zero ambient screen recording, and strict component ownership protection.

## ADR-013: Research-Gap Closure via Independent Policy Broker and Component Segregation
Status: accepted. Benchmarking against seven competitive and prior art systems across eight core dimensions establishes that SYSTEM MIND X addresses five critical industry research gaps: Gap 1 (AI-Native Policy-Broker Disconnect), Gap 2 (Component Ownership Vacuum & Dependency Clobbering), Gap 3 (The 'Scan is Safe' Fallacy & Ambient Host Execution), Gap 4 (Screen Ephemerality vs Persistent Temporal Digital Twin), and Gap 5 (The All-or-Nothing Privilege Trap). Full native compliance across all dimensions is enforced as an architectural invariant.

## ADR-014: Six-Zone Trust Boundary Architecture and STRIDE Threat Model
Status: accepted. SYSTEM MIND X formally stratifies system operations across six hierarchical Trust Zones (Zone 0: Untrusted External, Zone 1: User Space, Zone 2: AI Control Plane, Zone 3: Deterministic Policy Engine, Zone 4: Privileged Broker, Zone 5: Kernel & Hardware). Transitions must strictly obey the Rule of Strict Adjacency (AI Control Plane Zone 2 cannot bypass Policy Engine Zone 3 to reach Broker Zone 4 or Kernel Zone 5) and the Rule of Untrusted External Non-Execution (Zone 0 binaries can never execute in Zone 1/5 without verified containment). All six STRIDE threat categories (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege) are cataloged into typed threat vectors with verified architectural mitigations.

## ADR-030: File Trust State Machine and Supported File-Handler Policy
Status: accepted. SYSTEM MIND X formalizes a discrete eight-state File Trust State Machine (UNTRUSTED_UNKNOWN, QUARANTINED, STATICALLY_INSPECTED, SANDBOX_VERIFIED, USER_ATTESTED, VENDOR_SIGNED_VERIFIED, SYSTEM_CORE_IMMUTABLE, BLOCKED_MALICIOUS) and a Supported File-Handler Policy (DENIED, STATIC_PARSER_ONLY, HARDENED_ISOLATED_VIEWER, DISPOSABLE_SANDBOX_EXECUTION, NATIVE_HOST_EXECUTION). Under the inviolable 'Scan != Safe' invariant, static inspection or antivirus clearing moves a file to STATICALLY_INSPECTED at best and strictly prohibits native host execution. Quarantined and untrusted files are restricted to unprivileged static parsers or isolated micro-VM sandboxes. Native host execution is strictly restricted to immutable OS core binaries, verified vendor-signed binaries, or user-attested files with explicit human consent.

## ADR-031: Typed Action Contracts, Precondition/Postcondition Rules, and Atomic Rollback
Status: accepted. SYSTEM MIND X replaces unstructured shell commands with strongly typed action contracts (TypedActionContract) governed by deterministic Precondition and Postcondition rules. Consequential operations (MEDIUM_IMPACT, HIGH_IMPACT, CRITICAL_PRIVILEGED) strictly mandate explicit pre-execution readiness predicates and post-execution state verification predicates. High and critical operations mandate an executable RollbackContract (snapshot revert, file restore, service restore, or package downgrade). Contract parameters are sanitized against shell metacharacters and command injection patterns. The Layer 6 Trusted Broker is mathematically prohibited from capability dispatch if any precondition fails, and automatically invokes the rollback contract if any postcondition fails.

## ADR-032: Identity, Role-Based Authority, and Deterministic 4-Tier Policy Precedence
Status: accepted. SYSTEM MIND X formalizes explicit caller identities (LOCAL_CONSOLE_USER, AI_COGNITIVE_PLANNER, AUTONOMOUS_MAINTENANCE_DAEMON, ENTERPRISE_MDM_ADMIN, SANDBOXED_PEER_AGENT) and role-based authority boundaries (SecurityRole). The PolicyPrecedenceEngine resolves authorization through a strict, deterministic four-tier hierarchy: Tier 1 (Supreme) Hard Charter Invariants (SC-01 to SC-08), Tier 2 Enterprise Organization Policies, Tier 3 User Explicit Safety Policies, and Tier 4 AI Planner Heuristic Proposals. Higher tiers strictly override lower tiers; Tier 1 hard invariants cannot be bypassed by any user, administrator, or enterprise policy. Dual authorization (TWO_PERSON_OR_BREAK_GLASS) mandates confirmed biometric authentication for critical privileged operations.

## ADR-033: Immutable Cryptographic Audit Ledger, Automated Secret Redaction, and Tiered Data Retention
Status: accepted. SYSTEM MIND X implements an append-only, tamper-evident cryptographic audit ledger (ImmutableAuditLedger) in Layer 6. Every consequential action, policy decision, approval, capability dispatch, state mutation, and rollback is recorded with strictly monotonic sequence numbers, canonical payload hashes, and SHA-256 hash-chain linkage (prev_event_hash). The SecretRedactor recursively scrubs credentials, API tokens, passwords, session tokens, and private keys before hashing or persistence. A 5-tier data retention taxonomy governs storage lifecycles (from 48-hour ephemeral traces to 365-day immutable critical security events). When expired non-critical records are pruned, a ChainCheckpointRecord anchors the hash chain, maintaining unbroken mathematical verification.

## ADR-034: Unified API Wire Envelopes, RFC 7807 Structured Error Model, and SemVer Negotiation
Status: accepted. SYSTEM MIND X standardizes IPC and service communications across all execution planes through typed Request (`ApiRequest`) and Response (`ApiResponse`) wire envelopes, an RFC 7807-inspired structured error model (`ApiErrorDetail`), and SemVer 2.0.0 client-server negotiation (`VersionNegotiator`). Wire envelopes mandate globally unique request IDs, dot-delimited method URNs, caller identity headers, and mandatory idempotency keys (`idempotency_key`) for all mutating operations to prevent duplicate execution. Machine-readable error codes (`E1000..E7999`) across seven functional domains enforce actionable remediation hints and retryability semantics, while `ApiErrorFactory` integrates with `SecretRedactor` to guarantee recursive scrubbing of API tokens, passwords, and private credentials from diagnostic error payloads. Major version changes enforce a minimum 6-month deprecation warning cycle before method retirement.

## ADR-036: Monorepo Topology, Top-Level Workspace Boundaries, and Dependency Isolation
Status: accepted. SYSTEM MIND X organizes the codebase as a strictly boundary-enforced polyglot monorepo governed by a machine-readable manifest (`monorepo.json`), boundary documentation per zone (`README.md`), and automated CI verification (`MonorepoBoundaryValidator`). Six canonical top-level zones partition the system: `apps/` (Layer 7 Desktop UI in TypeScript/React & Tauri), `crates/` (Layer 1, 2, 6 Native Daemon and OS sensors in Rust), `src/` (Layer 3, 4, 5, 6 Cognitive Planner, Digital Twin, and Policy in Python), `schemas/` (Layer 6, 7 language-neutral contracts in JSON Schema / Cap'n Proto), `tools/` (developer tooling and release verification), and `docs/` (architectural specifications). To uphold architectural security invariants, strict unidirectional dependency rules are enforced: `apps/` and `src/` cannot directly import internal `crates/` source or call native OS APIs without wire mediation; `crates/` cannot depend on Python runtimes; `schemas/` must remain completely self-contained; and `tools/` cannot be packaged into production daemon or UI artifacts.

## ADR-087: Application Lifecycle Tracking, Observable State Transitions, and Point-in-Time Application History

## ADR-088: Process Start and Exit Tracking, PID Recycling Collision Resistance, and Historical Execution Observability
Status: accepted. SYSTEM MIND X establishes the process lifecycle tracking architecture (`src/system_mind/twin/process_lifecycle.py`), schema migration `0012` (`src/system_mind/database/migrations/0012_process_lifecycle_events.sql`), packaging validator (`src/system_mind/packaging/process_lifecycle.py`), design specification (`docs/design/DAY_077_PROCESS_START_AND_EXIT_TRACKING.md`), developer CLI tool (`tools/detect_process_lifecycle.py`), and test suite (`tests/test_process_lifecycle.py`). To enable the temporal digital twin to track process creation, execution ancestry, and termination across multiple telemetry channels (periodic process table polling and real-time Apple Endpoint Security / OS event notifications), the architecture mandates: (1) PID collision-resistant canonical entity URN derivation (`INV-PROC-01`): every process entity references a canonical URN `urn:systemmind:proc:<device_id_8>:<start_epoch_ms>:<pid>:<path_digest>` binding device ID, start timestamp, PID, and executable path digest, guaranteeing that rapid Unix PID recycling never results in primary key collisions or entity confusion across execution intervals; (2) Temporal boundedness and runtime invariants (`INV-PROC-02`): for any exited process, $\text{start\_epoch\_ms} \le \text{exit\_epoch\_ms}$ and $\text{runtime\_ms} = \text{exit\_epoch\_ms} - \text{start\_epoch\_ms}$; (3) Component ownership guardrails (`SC-02` / `INV-PROC-03`): all process lifecycle events capture `ownership` (`SYSTEM_MANAGED`, `VENDOR_MANAGED`, `USER_MANAGED`); user processes are observed strictly in read-only mode with zero autonomous termination or unprompted modification; (4) Universal 'Scan != Safe' invariant enforcement (`SC-03` / `INV-PROC-04`): enforced at SQLite database constraint level (`CHECK (scan_proves_safe = 0)`) and in Python dataclasses (`scan_proves_safe: bool = False`); logging process execution reflects observed telemetry, never safety or benign intent; (5) Multi-channel observation ingestion (`INV-PROC-05`): process lifecycle transitions are detected through periodic process table diffing (`diff_process_tables` handling new starts, terminations, and recycled PIDs) and mapped from real-time OS event streams (`from_endpoint_security_event` for `NOTIFY_EXEC`, `NOTIFY_FORK`, `NOTIFY_EXIT`); (6) Append-only event store integration (`INV-PROC-06`): process events bridge directly to `SystemEventStore` as `PROCESS_SPAWNED` and `PROCESS_EXITED` with contiguous sequence numbers and cryptographic SHA-256 hash chaining; (7) Lossless property graph synchronization (`INV-PROC-07`): `ProcessLifecycleTracker.sync_with_digital_twin` updates the in-memory `DigitalTwinGraph`, adding `PROCESS` entities with `HOST -> CONTAINS -> PROCESS`, `PROCESS -> SPAWNED_BY -> PARENT`, and `APP -> OWNS -> PROCESS` relationships; exited processes are marked stale (`is_stale = True`), NEVER deleted from history; (8) Point-in-time process reconstruction (`INV-PROC-08`): `ProcessLifecycleManager.get_running_processes_at` accurately reconstructs the exact set of active processes on any device at any historical Unix epoch timestamp using $\text{MIN(start\_epoch\_ms)} \le T \land (\text{MAX(exit\_epoch\_ms)} \text{ IS NULL} \lor \text{MAX(exit\_epoch\_ms)} > T)$; and (9) Zero ambient shell authority (`SC-01` / `INV-PROC-09`): all process tracking, diffing, and database interactions execute purely in-memory via parameterized SQL statements without spawning shell processes (`shell=False`).
